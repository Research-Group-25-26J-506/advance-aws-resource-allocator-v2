# Prompt: Gateway OTel Collector Config

## Goal
Produce `infrastructure/observability/otel-gateway.yaml` — heavy-processing collector as an
ECS Fargate service.

## Constraints
- Receivers: otlp; prometheus (self-scrape).
- Processors: memory_limiter (1500 MiB / spike 200); **tail_sampling**: 100% errors, 100% latency
  > 1 s, 100% of ops in {provision, deploy, sync}, 5% of the rest; resourcedetection (env, ec2,
  ecs); batch (10s / 5000).
- Exporters: prometheusremotewrite (AMP, SigV4); otlp/tempo; loki.
- Pipelines: traces → tail_sampling → tempo; metrics → prometheusremotewrite; logs → loki.
- Extensions: sigv4auth for AMP.
- ECS Fargate service, min 2 tasks, target-tracking auto-scaling CPU 60%, behind an internal NLB.

## Acceptance
`otelcol validate` passes. Load test at 1000 spans/s shows no drop.

## Enhancements (v2.1)
- **Tail-sampling + multiple tasks caveat made explicit:** spans of one trace must land on one
  collector. Use NLB flow hashing only as a stopgap; correct fix is a two-layer gateway
  (loadbalancing exporter with routing_key: traceID in front of samplers). Document the chosen
  topology in an ADR.
- Collector self-telemetry pipeline enabled (its own metrics to AMP): queue depth, dropped spans,
  refused points — these get alert rules in 4.12.
- Loki exporter maps only bounded labels (service, env, level); everything else stays in the log
  body — protects Loki from label-cardinality explosions.
