# Prompt: Deploy CloudFormation Stacks

## Goal
Produce `.github/workflows/deploy.yaml` — deploys infrastructure and ECS services per environment.

## Constraints
- Trigger: workflow_run of build-images success. GitHub environments platform-dev (auto),
  platform-stg (auto after dev), platform-prod (manual approval).
- Stack order: network → data → auth → observability → compute → iam.
- Per stack: `aws cloudformation deploy --no-fail-on-empty-changeset --capabilities
  CAPABILITY_NAMED_IAM`; change sets created, described, applied; summary posted as PR comment
  when applicable.
- After compute: `aws ecs update-service --force-new-deployment`; `aws ecs wait services-stable`.
- Post-deploy smoke: curl /healthz on ALB DNS.
- On failure: rollback via cancel-update-stack or runbook link.
- Grafana deployment-marker annotation. Slack #platform-deploys notification (SHA + env + status).

## Acceptance
Merge to main auto-deploys to dev within 30 minutes. STG only after dev green. PROD requires
approval.

## Enhancements (v2.1)
- Concurrency group per environment (`deploy-{env}`, no cancel) — two overlapping deploys to one
  env is how you get interleaved changesets.
- Deployment marker also written to an SSM parameter (`/platform/{env}/deployed-sha`) — the
  rollback workflow (7.12) and dashboards both read it.
- Migrations job (7.6) is an explicit dependency between data and compute in the job graph.
- iam stack ordering caveat: task-role changes needed by compute must deploy before compute —
  split iam into `iam-base` (early) and `iam-app` (late) if the cycle bites.
